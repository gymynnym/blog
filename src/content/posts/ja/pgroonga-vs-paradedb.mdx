# PGroonga vs ParadeDB：FTSの最強候補

## はじめに

> 2026年3月時点で、LogHubはPostgreSQLの多言語FTS拡張[PGroonga](/ja/posts/pgroonga-guide-1)で検索を実装しています。

最近、似た目的を持つ[ParadeDB](https://www.paradedb.com/)を見つけました。どちらもPostgreSQL拡張として動き、Elasticsearchなどの別のエンジンを運用せずに強力なFTSを実現します。ただ、ライブラリや内部構造、使い方はかなり違います。

今回は、**PGroongaとParadeDBを韓国語全文検索の観点から比較**します。

## 機能の違い

簡単にまとめると次のとおりです。

| 項目             | PGroonga       | ParadeDB   |
| ---------------- | -------------- | ---------- |
| 内部エンジン     | Groonga        | Tantivy    |
| トークナイザー   | Mecab/Mecab-ko | Lindera    |
| スコアリング     | TF             | BM25       |
| スコア関数の利用 | 比較的冗長     | 比較的簡単 |
| 独自の同義語辞書 | 対応           | 非対応     |

### 内部エンジン

PGroongaはC製の[Groonga](https://github.com/groonga/groonga/)を使い、後述するTFによるキーワード検索を行います。

ParadeDBはRust製の[Tantivy](https://github.com/quickwit-oss/tantivy)を使い、後述するBM25を採用しています。

### トークナイザー

PGroongaは**標準で韓国語トークナイザーを提供しません**。今回は[Mecab-ko](https://bitbucket.org/eunjeon/mecab-ko)とmecab-ko-dic辞書を追加しました。

> 日本語用Mecabと韓国語用Mecab-koのインターフェースが同じことを利用しています。[PGroongaで韓国語トークナイザーを使う](/ja/posts/pgroonga-guide-5)で詳しく説明しています。

ParadeDBは**標準で韓国語トークナイザーに対応**します。Rust製の[Lindera](https://github.com/lindera/lindera)は辞書があれば**CJK（中国語・日本語・韓国語）**を処理できます。韓国語にはMecab-ko-dicをもとにした**[KoDic](https://github.com/lindera/mecab-ko-dic)**を使います。

### スコアリング

FTSの**スコアリング**は関連度の計算です。Groongaは標準でTF、TantivyはBM25を使います。

- **TF（Term Frequency）**：検索語の出現回数を数えます。
- **BM25（Best Matching 25）**：TF＋IDF＋avgDL＋その他。
  - `IDF`：全体での単語の希少性。
  - `avgDL`：平均文書長。

![bm25.png](https://assets.akuk.in/blog/in-content/1772795045136_bm25.webp 'Wikipediaから引用したBM25の式')

GroongaはBM25を提供しません。TFとフィールドごとの重みを開発者が調整する、意図的な設計です。

> 一般にTFはBM25より高速です。

### スコア関数の利用

関連度関数の呼び出しは**ParadeDBのほうが簡単**です。

`pgroonga_score`には`ctid`と`tableoid`を渡します。PostgreSQLの内部識別子なので、ORMでは扱いにくい場合があります。

`pdb.score`はインデックス作成時に`key_field`で指定した一意のIDだけを受け取ります。内部フィールドを追加・公開せず、ORMでも使いやすくなっています。

### その他

PGroongaはGoogle検索に似た[Groongaクエリ構文](https://groonga.org/docs/reference/grn_expr/query_syntax.html)をサポートし、複雑な利用者の検索も追加実装なしで扱えます。`pgroonga_condition`で重みを設定し、`pgroonga_query_expand`で独自の同義語辞書も作れます。

ParadeDBはTantivy構文を使い、独自の同義語辞書には対応していません。

> 2026年3月時点のParadeDBは`0.21.x`で、まだ正式リリースの状態ではありません。

## ベンチマーク環境

Dockerで環境を分けてテストしました。

#### docker-compose.yml

```yml
services:
  my-pgroonga:
    container_name: my-pgroonga
    image: ghcr.io/akuk.in/postgres:0.2.0
    shm_size: 1g
    volumes:
      - ./pgroonga/init/:/docker-entrypoint-initdb.d/
    env_file: .env.postgres
  my-paradedb:
    container_name: my-paradedb
    image: paradedb/paradedb:latest
    shm_size: 1g
    volumes:
      - ./paradedb/init/:/docker-entrypoint-initdb.d/
    env_file: .env.postgres
```

韓国語トークナイザー用にカスタムイメージが必要なので、PGroongaとMecab-koを含むLogHubの`ghcr.io/akuk.in/postgres:0.2.0`を使いました。

ParadeDBには韓国語トークナイザーが入っているため、公式イメージを使いました。

`.env`にはユーザー名とパスワードだけを設定しています。

#### pgroonga/init/01-ddl.sql

PGroonga用のサンプルテーブルを作ります。

```
\c postgres

CREATE EXTENSION IF NOT EXISTS pgroonga;

CREATE TABLE IF NOT EXISTS public.posts (
    id                  bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    title               text         NOT NULL,
    content             text         NOT NULL,            -- for search
    topics_flat         text         NOT NULL DEFAULT ''  -- for search
);

CREATE INDEX IF NOT EXISTS posts_fts_idx ON public.posts
USING pgroonga (
  (ARRAY [title, content, topics_flat]))
WITH (
  tokenizer='TokenMecab',
  normalizer='NormalizerAuto'
);
```

1. `pgroonga`を有効にします。
2. `posts`テーブルを作ります。
3. `posts`にFTSインデックスを設定します。
   - Mecab-koを使います。

#### paradedb/init/01-ddl.sql

ParadeDB用のサンプルテーブルを作ります。

```
\c postgres

CREATE EXTENSION IF NOT EXISTS pg_search;

CREATE TABLE IF NOT EXISTS public.posts (
    id                  bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    title               text         NOT NULL,
    content             text         NOT NULL,            -- for search
    topics_flat         text         NOT NULL DEFAULT ''  -- for search
);

CREATE INDEX IF NOT EXISTS posts_fts_idx ON public.posts
USING bm25 (
  id,
  (title::pdb.lindera(korean, 'trim=true', 'remove_short=2')),
  (content::pdb.lindera(korean, 'trim=true', 'remove_short=2')),
  (topics_flat::pdb.simple)
)
WITH (key_field = 'id');
```

1. `pg_search`（ParadeDB）を有効にします。
2. `posts`テーブルを作ります。
3. `posts`にFTSインデックスを設定します。
   - Lindera（Korean）を使います。

#### Faker.jsでシードデータを作る

ベンチマーク用のシードデータを作るため、**韓国語に対応した使いやすい偽データ生成ツール**[Faker.js](https://fakerjs.dev/)を使いました。

Faker.jsはさまざまな偽データを生成でき、テスト用テキストも簡単に作れます。それを使ってシード生成スクリプトを書きました。

```js
import fs from 'fs';
import { fakerKO as faker } from '@faker-js/faker';

const NUM_ROWS = 1_000_000; // 生成するダミーデータの件数
const OUTPUT_FILE = '02-dml.sql';

const techPool = [
  { key: 'java', name: 'Java' },
  { key: 'cpp', name: 'C++' },
  { key: 'python', name: 'Python' },
  { key: 'javascript', name: 'JavaScript' },
  { key: 'react', name: 'React' },
  { key: 'spring', name: 'Spring' },
  { key: 'nodejs', name: 'Node.js' },
  { key: 'postgres', name: 'PostgreSQL' },
  { key: 'aws', name: 'AWS' },
  { key: 'docker', name: 'Docker' },
];

let sqlContent = ``;

for (let i = 0; i < NUM_ROWS; i++) {
  const title = faker.lorem.sentence();
  const content = faker.lorem.paragraphs(3);
  const selectedTopics = faker.helpers.arrayElements(techPool, { min: 1, max: 3 });
  const topicsFlat = selectedTopics.map((topic) => `${topic.key},${topic.name}`).join(':');

  const safeTitle = title.replace(/'/g, "''");
  const safeContent = content.replace(/'/g, "''");
  const safeTopics = topicsFlat.replace(/'/g, "''");

  sqlContent += `INSERT INTO public.posts (title, content, topics_flat) VALUES ('${safeTitle}', '${safeContent}', '${safeTopics}');\n`;
}

fs.writeFileSync(OUTPUT_FILE, sqlContent, 'utf-8');
```

### ベンチマークと結果

環境は次のとおりです。

- PostgreSQL 18
- `shm_size` : 1g
- ストレージ：NVMe SSD（PCIe 3.0）。

使ったクエリは次のとおりです。

> 構文が違うため、完全に同じ結果を出せるクエリは限られていました。

```sql
-- PGroongaのクエリ
SELECT id, title
FROM public.posts
WHERE ARRAY[title, content, topics_flat] &@~ pgroonga_condition(
    query => ?1,
    weights => ARRAY[5, 2, 3],
    index_name => 'posts_fts_idx'
)
ORDER BY pgroonga_score(tableoid, ctid) DESC;
```

```sql
-- ParadeDBのクエリ
SELECT id, title
FROM public.posts
WHERE (
    title &&& ?1::pdb.boost(5)
    OR content &&& ?1::pdb.boost(2)
    OR topics_flat &&& ?1::pdb.boost(3)
)
ORDER BY pdb.score(id) DESC;
```

どちらもAND条件で検索語を含むか確認し、関連度の降順で返します。

同じクエリを1,000回実行した、ウォームキャッシュでの平均値です。

| 項目                   | PGroonga + Mecab-ko | ParadeDB + Lindera |
| ---------------------- | ------------------- | ------------------ |
| FTSレイテンシー        | 881ms               | 1112ms             |
| 同時INSERTレイテンシー | 1531 ms             | 254ms              |
| 同時INSERT TPS         | 6.53                | 39.30              |

> `pg_bench`で測定しました。

平均FTS読み取りではPGroongaとMecab-koが約1.3倍速く、書き込み（インデックス更新）ではParadeDBが約6倍速い結果でした。

サイズも比較しようとしましたが、ParadeDBは`pg_relation_size`で確認できる一方、PGroongaはGroongaの別ストレージを使うため難しい状況でした。[関連Issue](https://github.com/pgroonga/pgroonga/issues/15)。:(

### 疑問：なぜ関連度が違うのか？

同じ重みを付けたのに、並び順が大きく違い、一部の行がない場合もありました。

Linderaが正常に動いているか疑問に思い、トークン化の結果を確認しました。

```sql
SELECT array_agg(token->>'value') AS tokens
FROM json_array_elements(
  (pgroonga_command(
    'tokenize TokenMecab "계승/발전과 범죄에 의무교육은 범죄에 장기 판결이 조약과 기능을 범죄를 청구할 수 있다."'
  )::json)->1
) AS token;
-- {계승,/,발전,과,범죄,에,의무,교육,은,범죄,에,장기,판결,이,조약,과,기능,을,범죄,를,청구,할,수,있,다,.}

SELECT '계승/발전과 범죄에 의무교육은 범죄에 장기 판결이 조약과 기능을 범죄를 청구할 수 있다.'::pdb.lindera(korean)::text[] AS tokens;
-- {계승,발전,과,범죄,에,의무,교육,은,범죄,에,장기,판결,이,조약,과,기능,을,범죄,를,청구,할,수,있,다}
```

トークナイザーには問題がなく、Tantivy構文でも結果は同じでした。

原因は前述のスコアリングの違いでした。PGroongaはTFで出現回数を数えますが、ParadeDBのBM25はより多くの変数を考慮します。

アプリケーションの特性に合うほうを選べばよさそうです。

## おわりに

PostgreSQLの全文検索拡張PGroongaとParadeDBを簡単に比較しました。

**LogHubにParadeDBを実験的に導入する予定**です。主な理由は大幅に低いインデックス更新コスト、つまり同時書き込み性能です。ORMで扱いにくい`ctid`や`tableoid`を外せる点も魅力です。

独自の同義語辞書やGroonga構文が使えなくなるトレードオフもあり、正式リリース前なので、まず実験環境で試します。

Rust製の強力なTantivyをPostgreSQL内で直接使えるのは魅力的です。より精密で質の高い結果を目指せるBM25にも感心します。
