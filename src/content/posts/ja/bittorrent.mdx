# BitTorrent：世紀初頭の情報配布方法

> 本記事は[BEP 52](https://www.bittorrent.org/beps/bep_0052.html)に基づくBitTorrent v2を扱います。

> 開発者Bram Cohenの[BitTorrent論文](https://www.bittorrent.org/bittorrentecon.pdf)を分かりやすく紹介します。v1に固有の内容は扱いません。

BitTorrentは、大きなファイルを効率的に配布するためのP2P（Peer-to-Peer）転送システムです。決して違法ファイル共有のためのプロトコルではありません！！！

## 1. BitTorrentの仕組み

### 1.1. P2P(Peer-to-Peer)

HTTPでは通常、アップロードの負担がサーバーに集中します。BitTorrentでは同じファイルを取得する利用者が**互いにアップロード**して負担を分散し、最初の配布者のホスティング費用を減らします。

### 1.2. ピースへの分割

BitTorrentは一つの連続ストリームではなく、ファイルを**ピースに分割**して転送します。通常は数百KB～数MBで、順番どおりには転送されません。ハッシュによる完全性検証にも使います。

全体を持たないピアでも手元の部分を配布でき、最終的に完全なファイルを届けられます。特定のアップローダーへの依存も減ります。

転送に失敗しても、そのピースだけ再要求すればよいため、効率と安定性が向上します。:)

> 実際の転送では、ピースをさらに小さな**ブロック**に分けます。通常は16KBです。

### 1.3. シーダーとリーチャー

ピアは大きく**シーダー**と**リーチャー**に分かれます。

- **シーダー**：全体を持ち、ダウンロードしないピア。
  - 他のピアにアップロード（シーディング）します。
- **リーチャー**：全体を持たず、ダウンロード中のピア。
  - 手元のピースを送り、不足分を取得します。

### 1.4. トラッカー

**トラッカー**はピア同士を見つけるサービスです。P2Pですが、探索には中央のサービスも使います。ダウンローダーがファイルや待ち受けポートを伝えると、同じファイルを共有するピアの接続情報が返され、それを使って接続します。

> トラッカーの役割は、ピア同士の発見を助けることに厳しく限られています。

## 2. BitTorrentプロトコル

### 2.1. `.torrent`ファイル

配布には、Webサーバーなどに`.torrent`を公開します。実際の内容は含まず、次の情報を持ちます。

- `announce`：トラッカーURL（必須）。
- `announce-list`：announceが使えない場合の複数トラッカーURL。
- `creation date`：作成時刻。
- `created by`：作成プログラムの名前とバージョン。
- `comment`：作成者のコメント。
- `encoding`：UTF-8などの文字コード。
- `piece layers`：各ファイルのピースのハッシュ。
- `info`
  - `meta version`：プロトコルバージョンの整数。
  - `piece length`：転送するピースの大きさ。
  - `name`：最上位のディレクトリ名かファイル名。
  - `file tree`：ファイル構造とハッシュの階層辞書。

この情報を使って、ダウンローダーはBitTorrentに参加できます。

```json
// ファイルツリーの例
{
  "movie.mp4": {
    "": {
      "length": 145020304,
      "pieces root": "<32-byte-binary-hash>"
    }
  },
  "subs": {
    "kor.srt": {
      "": {
        "length": 30204,
        "pieces root": "<32-byte-binary-hash>"
      }
    }
  }
}
```

### 2.2. ピア探索

参加するには、同じ内容を共有するピアのIP:portを探します。次の方法があります。

1. **トラッカー方式**：torrent内のサーバーへ問い合わせます（中央集権型）。
   - 最も伝統的な方法です。
2. **DHT（Distributed Hash Table）**：トラッカーなしで探します（分散型）。
   - 主な概念：
     - ファイルIDとノードIDは同じ32バイトです。
     - ファイルIDに最も近いノードIDを持つ通常8個以上のノードが、アドレス帳を管理します。
       - そのためDHTノードは、望むかどうかに関係なく**一時的なトラッカー**になります。
       - 複数のノードで管理し、ネットワークの維持と安全性を高めます。
     - ランダムではなく**Kademliaの距離に基づく探索**を使います。
       - XORで二つのIDの近さを測ります。
     - 核心は**特定ファイルのアドレス帳を見つけること**です。
   - シーダーの登録手順：
     1. ファイルIDを確認します。
     2. DHTで最も近いノードを探します。
     3. 自分のアドレスを保存するよう頼みます。
   - リーチャーの検索手順：
     1. 必要なファイルIDを確認します。
     2. DHTで最も近いノードを探します。
     3. ファイルのアドレス帳を要求します。
3. **PEX（Peer Exchange）**：接続済みのピアから別のピアを紹介してもらいます。
   - 最初の接続が必要なので補助的な方法です。
4. **LPD（Local Peer Discovery）**：LAN内のピアを探します。
   - 内部ネットワークにマルチキャストで探索信号を送ります。
   - 外部ネットワークを通らず、高速で帯域も節約できます。

> アドレス帳を管理するノードによる中間者攻撃が気になったら、後の安全性の節で扱うので、先に読んでも構いません。

### 2.3. ピースのダウンロード

連続ストリームではなくピースごとに転送し、すべて受け取って結合することで元のファイルを完成させます。

複数ピアから並列取得でき、完全性の検証も行えます。検証には`file tree`内の各ファイルの`pieces root`と、別の`piece layers`を使います。

**要求と転送の流れ**は次のとおりです。

1. `piece layers`のハッシュ一覧を取得します。
2. 必要なピースを持つピアを探します。
3. ピースを要求して受け取ります。
4. 完全性を検証します（Merkle Proof）。
   - ピースを分割したブロックのハッシュを計算します。
   - Merkle木に沿って上位へ結合・ハッシュし、**ピースのハッシュ**を作ります。
   - `piece layers`の該当ハッシュと比較します。
     - 一致すれば保持して通知します。
     - 不一致なら破棄して再要求します。

取得順は性能に重要です。次の**選択戦略**を使います。

- **Strict Priority**：要求したピースのブロックを優先します。
  - 完全なピースを早く確保できます。
- **Rarest First**：最も希少なピースを先に取得します。
  - 持っているピアが少ないものほど希少です。
  - 貪欲な取得が全体の可用性を高めます。
- **Random First Place**：初期はランダムに選び、早く参加します。
- **Endgame Mode**：完了直前の残りを全ピアに要求します。
  - 遅いアップローダーで取得が停滞することがあります。
  - 残りを持つすべてのピアへ要求します。
  - 届いたら要求を取り消して帯域の無駄を防ぎます。

### 2.4. ピースの結合

順不同で届くため、正しいオフセットに書き込みます。取得後にバイナリを結合して**完全なファイル**を作れます。

### 2.5. シーディング

全体を持つと**シーダー**になります。取得後も一定期間**シーディング**を続けることが、エコシステムの維持に重要です。

## 3. TCP, UDP, uTP(μTP)?

### TCP vs UDP

TCPとUDPの両方を使います。以前は主にTCPでしたが、帯域を使い切る問題に対応するため、現在のクライアントはUDPをよく使います。

### uTP(μTP)

そのままのUDPではなく、信頼性と輻輳制御を加えたuTP（μTP）を使います。他の通信を検知すると速度を調整します。

uTP（μTP）はMicro Transport Protocolの略で、μTorrentが開発しました。μが入力しづらいためuTPとも書きます。μTorrentは単なるスパイウェア・広告会社ではありません！

> uTPはファイル共有用で、DHTなどは通常のUDPを使います。

## 4. チョーキング

### チョーキングとは？

**チョーキング**は、特定のピアへのアップロードを一時的に止める状態です。

- **Choked**：データを送らず、要求も拒否します。
- **Unchoked**：要求があれば送れる状態です。

### いつ、なぜチョークするのか？

P2Pではピアの帯域が重要です。速いピア同士を優先すると効率的で、**十分にアップロードしないピア**はチョーク対象になります。

### いつ、なぜ解除するのか？

通常は10秒ごとに**対象を見直し**、速くやり取りする上位のピア（通常4個）を解除します。リーチャーは速く送る相手、シーダーは速く受け取る相手を優先します。

> 性能だけで選ぶと、新しいピアには受信の機会がありません。

そこで**楽観的解除**として、30秒ごとにランダムなピアを選んで速度を試します。速く応答すれば解除の一覧に加わります。

> **Snubbing**は相手がデータを送らず無視する状態で、通常60秒を目安に判断します。

まったくアップロードしないピアもいます。これを**Snubbing**とみなし、**Anti-Snubbing**という報復戦略でチョークし続けます。関係を回復できるのは楽観的解除だけです。

## 5. 安全性と匿名性

公開ネットワークで動くため、匿名性を理解せず使うと個人情報が露出する場合があります。

### 5.1. プロトコル暗号化（MSE/PE）

多くのISPはP2Pを検知して帯域を制限します。[RC4](https://en.wikipedia.org/wiki/RC4)を使う**MSE/PE**で回避できますが、難読化に近く、IPは隠れません。**匿名性は保証しません**。

### 5.2. 匿名化

構造上の特徴でありリスクは、**全ピアのIPが公開されること**です。匿名化にはVPNやプロキシが必要ですが、ポート転送が動かず、十分に貢献できないピアになる可能性があります。

### 5.3. DHT攻撃（Sybil Attack）

前述のDHTでの中間者攻撃が**Sybil Attack**です。大量の偽ノードで一部領域を支配し、要求を横取りしてマルウェアを挿入したり盗聴したりします。

簡単で強力な対策は**ノードID生成の制限**です。ランダムなIDではなく**実際のIP**で生成させます。大量の公的IPが必要になり、攻撃の費用が高くなります。

> IP引数にランダムな値を入れればよいのでは？

IPは公開されるため、受信者は実際のIPとIDを比較し、本物か判断できます。

## 補足1：マグネットリンク

以前は**実体のある`.torrent`ファイル**が必要でした。URIの**マグネットリンク**ならリンクだけ共有でき、便利な方法としてよく使われます。

`magnet:`で始まり、次の構造を持ちます。

- `xt`：対象の一意のハッシュ（必須）。
  - `urn`：リソース名。
  - `btih`：BitTorrent情報ハッシュ。
- `dn`：取得前に表示する名前（任意）。
- `tr`：初期接続用のトラッカーURL（任意）。

> トラッカーURLは任意で、ファイル情報もありません！

URLがなければDHTだけで探索します。メタデータも他のピアから取得するため、ダウンロード開始が遅れる場合があります。

ただし分散型なので、特定のトラッカーに情報を伝える必要はありません。

## 補足2：NAT越え

家庭用PCの多くはNATの背後にあり、ポート転送なしで外から接続できません。クライアントは**UPnP（Universal Plug and Play）**でルーターにポートを自動開放させ、複雑な設定なしでアップロードできます。

> 逆に、利用者が明示的に決めなくてもポートが外部へ開放されます！
